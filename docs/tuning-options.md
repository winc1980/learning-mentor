# 調整項目と、その根拠の強さ

**読者：** 運営と、このリポジトリで実験を回す人。**配布物ではありません**（zip には入りません）。

利用者が触れうる設定のうち、**まだ選択肢として配れる段階にないもの**を、根拠の強さを付けて
置いておく場所。配れる状態になったものは
[learning-mentor-usage.md](../learning-mentor-usage.md) に移す。

**利用者に対する現時点の答えは「既定のまま使う」で統一してある。** ここに書いてあるのは、
その答えの裏側（なぜ推奨を出さないか）であって、利用者に読ませる前提の文章ではない。

## モデルの選び方

**[測定済]**（run 012・013。ただし範囲が狭い。下の「言えないこと」を必ず読むこと）

### 規定順守では、選ぶ理由が無い

**広い質問（経路2）を踏ませても、現行の配布本文なら opus も sonnet も崩れない。**
同じ本文・同じ台本・同じ fixture で、`model` の1行だけを変えて測った。

| 条件 | sonnet（012） | opus（013） |
|---|---|---|
| 挨拶だけ → 広い質問 | 10/10 | 10/10 |
| 1ファイル解説 → 広い質問 | 10/10 | 10/10 |
| リポジトリ全体 → 広い質問 | 8/10 | 9/10 |

（数字は「解説を始める前に理解確認をしたか」。各10判定＝n=5 × 盲検採点者2名）

**「大事な場面ほど上位モデル」は逆効果、という見立ては現行本文では成り立たない。**
かつて opus が同じ条件で 0/10 まで落ちたのは事実だが（run 002）、それは
**v2-gate 取り込み前の本文**での話で、パッチは 2026-09-07 に配布本文へ入っている。
**あれはモデルの性質ではなく、本文の性質だった。**

### 差が出るのは、説明量と費用

両モデルとも規定を守っている状態での比較なので、**崩壊分は入っていない。**

| | sonnet | opus |
|---|---|---|
| 初手の応答（広い質問に対して） | 中央 **603 字** | 中央 **836 字**（約 1.4 倍） |
| 15セル / 30ターンの実費 | **$1.77** | **$3.57**（約 2.0 倍） |

**説明量の 1.4 倍は、本文を揃えて初めて見えた値。** 本文が違う run と比べると 3.9 倍に
見えるが、その差はほぼ全部がプロンプト版の違いであって、モデル差ではない。

### 言えないこと

- **「説明が長いほうが学習に効く」「短いほうが効く」とは書けない。**
  学習成果を一度も測っていない。長短は好みと使い勝手の軸であって、効果の軸ではない
  （[DECISIONS.md](../experiments/DECISIONS.md)）。選ぶ基準は運営が決めること
- **解説の分かりやすさ・正しさは測っていない。** 測ったのは規定を守るかどうかだけ
- **経路1（直前に詳細解説を済ませた状態）でのモデル差は測れていない。**
  sonnet はそもそもその状態に入らないため（run 011）。**「経路1に強い」ではなく
  「経路1の状態に入らない」**
- **レビュー／トラブルモードは未測定**（[#3](https://github.com/winc1980/learning-mentor/issues/3)）。
  本体プロンプトの約4割が一度も発火していない
- **3ターン目以降は未測定**（[#13](https://github.com/winc1980/learning-mentor/issues/13)）

**利用者に案内すること。** 既定（各ツールの標準モデル）のままで問題ない。
費用を抑えたい・多人数で回すなら sonnet を選んでよい。どちらでも規定は守られる。
変えて試した人がいた場合は、[動作確認](../README.md#3-動作確認するここを飛ばさないでください)を
やり直したうえで、
[フィードバックフォーム](https://docs.google.com/forms/d/e/1FAIpQLSeltEAaD7Q86DgPaqVQnhO84CIWZQl-eblp9zJ6hHeV5m66Lg/viewform)
に「モデルを変えたら、こう変わった」を書いてもらう。

## 版の選び方（現行版 / worked example 版）

**[未測定]**

**配っているのは現行版だけ。** worked example 版は実験ハーネスの中にしか存在しない。

| 版 | 何が違うか |
|---|---|
| **現行版**（配布中） | 完成コードを見せない。ヒントを段階的に具体化していく |
| **worked example 版**（`wex-fine`、ハーネス内のみ） | 完成コードを見せてよい。ただし**一度に 1 ブロックだけ**で、見せるたびに自己説明を挟む |

**なぜ 2 つ目があるか。** 学習会で「そもそも正解のコードを見せて解説してもらえた方が良い」
という声が出たため。この声自体は**どちらが学習に効くかの証拠ではない**が、
前提知識の乏しい学習者には完成例を見せたほうが効率が高い、という所見（worked example 効果）
はある。現行の配布物は「コードなし＋理解あり」と「コードあり＋理解なし（＝普通の AI）」の
二択しかなく、**「コードあり＋理解あり」が存在しない**。そこを埋める候補である。

**比較はこれから。** 結果が出るまで、選択肢としては提供しない。

## ここに書き足すとき

**この文書は、実験が進むたびに増えていく受け皿。** 書き足すときは：

1. **根拠の強さ（[測定済] / [観察] / [未測定]）を必ず付ける**
2. [測定済] には run 番号を添える
3. **[未測定] の項目に推奨を書かない。** 選択肢と「いま言えること」までにとどめる
4. **ただし利用者への案内は「既定のまま」と言い切る。** これは選択肢の優劣の主張ではなく、
   **変えないことの推奨**である。根拠が無いことと、利用者を迷わせたままにすることは別

もっともらしい推奨は、測る動機を消してしまう。
（この規律の理由：[concept.md](concept.md)、[CLAUDE.md](../CLAUDE.md)）

**配れる状態になったら、[learning-mentor-usage.md](../learning-mentor-usage.md) へ移す。**
そのとき根拠の強さの表示は落としてよい（利用者に必要なのは選び方であって、測定の履歴ではない）。
