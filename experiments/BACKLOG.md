**済んだこと。** 「メンターが理解確認を飛ばして一方的に解説する」現象を再現し、原因を2経路
（直前に詳細解説を済ませている／広い質問が来る）に特定し、プロンプト2箇所の修正で
崩壊していた4条件を 0〜2/10 から 10/10 に戻した。退行なし。

**測ったもの。** 102セル / 204ターン / 全12名の盲検採点。すべて opus、すべて固定台本。

**測っていないもの。** 下記のとおり、まだ大きい。

**2026-09-08 に本体を直した。** 実験の結果ではなく、読み直して見つかった不整合。

- **はしごの L3 と L4 が負荷と逆だった。** 選択式は原理的に必ず答えられるので予測より軽い。
  入れ替えて（新 L3=予測 / L4=選択）、予測を逃げ場から**既定手**へ、選択を**必ず着地できる最下段**へ位置づけ直した。
  合わせて「L4で答えられたら L3 へ上げる」を追加した（選択はまぐれで当たるが、予測は当たらないので、上げること自体がまぐれの検出になる）
- **ルーブリックを版2にした。** 版1（実験001〜006）とは L3/L4 の意味が逆。
  **記録側（`blind/`, `judgments.jsonl`, `report.md`, 凍結済み `variants/v2-gate.md`）は書き換えていない。** 読み替え規則は `rubric.md` に置いた
- **「1セッションで深く掘る箇所は2つまで」を撤廃した。** 分量は学習者の時間と気力で決まるもので、
  定数で縛る根拠がない。同じ節の「返事が短くなったら段を下げる」が適応的な保護として残るため、意図は失われない
- **運用ガイドが本体と食い違っていた。** 「5段階のはしご（… → 選択肢 → 予測）」と書かれており、
  段数も並びも本体と別物だった。`L5（予測）` という存在しない段への参照はここが出どころ

## 優先度A ── 穴が大きい

### A-1. レビューモードとトラブルモードが一度も動いていない ★最優先

**現状。** 204判定すべてが `モード=解説`、`五点セット収集=該当なし`。
6実験を通して**モード2（レビュー）とモード3（トラブルシューティング）は一度も発火していない。**

本体プロンプトの分量では、この2モードが約4割を占める。しかも規定が具体的で、
そのぶん破られたときに検出しやすい。

| モード | 未測定の規定 |
|---|---|
| **レビュー** | 説明ゲートが指摘より先に来るか／重大度ラベル（壊れる・危ない・改善余地・好み）／一度に上位3件まで／良い点を必ず1つ／修正コードを書かない |
| **トラブル** | 5点セットの収集（特に**本人の仮説**を聞いたか）／エラー文を一緒に読むか／実験を一緒に設計するか／答えを言わないか |

**なぜ重要か。** v2-gate は解説モードの手順1を補強した。**この修正が他モードに何をしたかは
まったく分かっていない。** 特にレビューの説明ゲートは解説の手順1と機能が近く、
干渉している可能性がある（良い方向にも悪い方向にも）。

**設計。** fixture の Issue 5（`application.tsx` が肥大化）と Issue 1（環境変数）が使える。

- レビュー：`app/routes/app/live/application.tsx` を指して「これ見てもらえますか」
- トラブル：`.env` 未設定で起動した想定のエラー文を貼って「動きません」

要因は「直前のターンの種類」を 004 と同じ3水準（`list_only` / `explain_one` / `explain_two`）
に据え、経路1がモードをまたぐかを見る。素と v2-gate の両方。

**規模。** 2モード × 3水準 × n=5 × 2プロンプト = 60セル / 120ターン。約 $15。
まず素のプロンプトだけ（30セル）で崩壊が起きるかを見て、起きたら v2-gate 側を回す。

**判定。** レビューで説明ゲートが飛ぶ条件があるか。トラブルで仮説を聞かずに答えを言う条件があるか。

### A-2. 実学習者との対話で一度も試していない

**現状。** 102セルすべてが固定台本で、相手は人間ではない。**外的妥当性の根拠がゼロ。**

固定台本には構造的な限界がある。学習者は台本どおりに答えないし、
沈黙する・話題を変える・不機嫌になる。メンタープロンプトの「負荷のサイン」
「逃げ道を常に開けておく」「返事が短くなったら段を下げる」は、
**相手が本当に疲れないと発火しない。**

**設計。** 実験ではなく観察から始める。

1. WINC の学習会で数名に `claude --agent learn` を使ってもらう
2. 同意を取ったうえでセッションログを保存
3. こちらは**介入せず**、崩れた箇所だけを収集する
4. 集まった崩れ方を、固定台本の条件に翻訳して再現実験にかける

**規模。** 実験コストはほぼゼロ。運営コストが本体。

**判定。** ここまでの6実験で見つけた2経路が、実際の会話でも観測されるか。
観測されない別の崩れ方が出てくるか（おそらく出る）。

**A-5（wex-fine）ができたので、観察は2本立てにできる。** 同じ学習者に両方を使ってもらい、
**どちらが好まれたかではなく、どちらで手が止まったか・どちらの説明が返ってきたかを見る。**
選好は聞かない。聞くと選好で決めたくなる。

**はしごの順序を直した効果（B-5）も、離脱の有無はここでしか見えない。**
予測は選択より負荷が高いので、固定台本では出ない疲れ方をする可能性がある。

### A-4. Codex CLI での配置が実際に成功するかの検証

**現状。** `learning-mentor-setup.md` は Codex CLI 向けに具体的な構成を指定しているが、
**一度も実機で試していない。** 机上で書いた手順がそのまま配布されている。

| 指定している項目 | 検証状況 |
|---|---|
| プロファイル `~/.codex/learn.config.toml` | 未検証 |
| `model_instructions_file` で組み込み指示を置換 | 未検証 |
| `sandbox_mode = "read-only"` **または** `default_permissions = ":read-only"` | 未検証。**2つ併記していること自体、どちらが現行か確信がない証拠** |
| 起動コマンド `codex --profile learn` | 未検証 |

**なぜ重要か。** 運用ガイドが繰り返し警告しているとおり、
**配置に失敗しても エラーは出ず、黙って無視される。** 学習者は「メンターを使っている」
つもりで通常の開発セッションと話し続けることになり、しかもそのセッションは
**編集ツールを持っている。** 「コードを書かせない」という設計目的が丸ごと崩れる。

さらに Codex は変化が速い。`~/.codex/prompts/` のカスタムプロンプトは既に非推奨（Skills へ移行）
になっており、**プロファイルと `model_instructions_file` も同じ経路をたどっている可能性がある。**
運用ガイド L206 が「この表は放置すると確実に古くなる」と名指しで警告しているのが、まさにここ。

**やること。** 測定実験ではなく配置検証。WINC メンバーと同じ手順を、こちらで一度なぞる。

1. Codex CLI を素の状態で入れ、`learning-mentor-setup.md` の記述**だけ**を見て配置する
   （記憶や推測で補わない。補わないと進めない箇所が、そのまま手順の穴）
2. **公式ドキュメントで各キーの現行性を確認する。** `model_instructions_file` が
   まだ存在するか、`sandbox_mode` と `default_permissions` のどちらが現行か
3. 運用ガイド L134-172 の動作確認4項目を Codex で実施する
   - **ツール一覧を出させる**（断り方では判定しない。ops-guide L144）
   - 短いコードを渡して、いきなりレビューが返らず説明ゲートが来るか
   - 3〜4往復させて「代わりに実装しましょうか」が出ないか
   - MCP を繋いだ場合、書き込み系ツールが1つも無いか
4. 詰まった箇所と、ドキュメントとの食い違いを記録する

**ここが Claude Code と決定的に違う点。** Claude Code は `--output-format stream-json` の
init イベントに**ハーネスが実際に渡したツール配列**が入るため、機械的に検証できた
（実験では全204ターンでこれを照合している）。**Codex に同等の機械可読な検証手段があるかは不明。**
無ければ、ツール一覧を自己申告させる手動確認に頼るしかなく、
運用ガイドが「自己申告では判定できない」と書いている状態に戻る。**まずここを調べる。**

**規模。** 実機作業 1〜2時間。API コストはほぼゼロ。

**判定と分岐。**

- **配置できて読み取り専用も確認できた** → setup.md の記述を「検証済み（日付）」に更新
- **手順が古い／動かない** → setup.md を修正。**動かない状態で配布し続けるのが最悪**
- **読み取り専用を機械的に確認できない** → setup.md に「Codex では能力の有無を機械的に検証できない」
  と明記し、**【A】常時適用型（学習用リポジトリを分ける運用）を推奨する**書き方に変える

**波及。** ここまでの実験結果はすべて Claude Code 上のもの。
**Codex を正式にサポートするなら、2経路の崩壊が Codex でも起きるかは別途測る必要がある**
（ハーネスは `claude -p` 前提なので、`codex exec` 相当に置き換える改修が要る）。
ただし優先度は低い。まず配置が成立するかが先。

**ついでにやると効率がよい。** 同じ機会に Copilot・Cursor・Gemini CLI の記述も確認する。
運用ガイドは「半年に一度、AIに公式ドキュメントで裏を取らせて更新する」と定めているが、
**その1回目がまだ実施されていない。**


### A-5. worked example 型（wex-fine）との比較 ★学習会フィードバック起点

**きっかけ。** 2026-09-08、WINC の web 学習会でデモを見せた参加者から
「そもそも正解のコードを見せて解説してもらえた方が良い」という意見が出た。

**証拠としての強さは限定的。** 見せたのは「タスク2に取り組みたい」とだけ書いた場合の
1往復目、1分弱。参加者自身がプロンプトを読んだわけではなく、粘られたときに
ヒントを具体化していく3段階（prompt.md L29-37）は実演できていない。
**「現行方式が学習に劣る」証拠ではなく、学習者がAIメンターに何を期待するかの表明**として扱う。

**それでも作る理由。** 現行の配布物は「コードなし＋理解あり」と「コードあり＋理解なし」
（quickstart が普通のAIへ逃がしている）の二択しかなく、**「コードあり＋理解あり」が存在しない。**
前提知識の乏しい学習者に完成例が効くという所見（worked example effect）もある。

**できているもの。** `variants/wex-fine.py` → `wex-fine.md`。
完成コードの禁止を外す代わりに、一度に見せる量を1ブロック（5〜15行・単体では動かない形）に絞り、
1ブロックごとに自己説明を挟む。**粒度そのものをコピペ耐性の機構にしている** ──
大きい塊は貼れば動くが、小さい塊は繋ぐ判断が要り、その判断が理解を強制する。
禁止は長い会話で摩耗するが、粒度は摩耗しない。

**最大の障害：主指標が使えない。** 現行ルーブリックは `完成コード相当: false` を遵守として採点する。
wex-fine ではこれが期待動作なので**極性が反転し、横並び比較ができない。**
**専用の指標を決めるまで着手しない。** 候補：

| 候補指標 | 何を捉えるか |
|---|---|
| 1応答あたりの提示ブロック数 | 1で止まったか。まとめて出していないか |
| 提示後の最初の問いの段 | L3（予測）から入ったか。L1・L2 に戻っていないか |
| 「まとめて出して」への応答 | 折れて全部出したか（C-2 の圧水準と同じ素材が使える） |

**設計。** 004 の3水準（`list_only` / `explain_one` / `explain_two`）で素と wex-fine を回す。
30セル / 60ターン。約 $8。

**対照を置くと仮説が測定になる。** 同じ内容をまとめて出す `wex-coarse` を作れば、
「粒度がコピペを防ぐ」は主張ではなく測定結果になる。+15セル。

**どちらが学習に効くかは、ここでは決まらない。** 固定台本で測れるのは規定の遵守だけ。
選好と学習効果は乖離することが知られているので、**参加者が「良い」と言ったことは判定に使えない。**
外的妥当性は A-2 に依存する。

## 優先度B ── 積み残し

### B-1. 「1ファイル解説 × 細かい質問」条件の揺れ

**現状。** 素のプロンプトで、002 の C は 4/10、004 の `explain_one` は 0/10。
**同一条件・同一プロンプトなのに run 間で振れている。** v2-gate 後はどちらも 10/10 なので
実害はないが、素の状態での揺れの原因が不明。

**なぜ気になるか。** run 間分散がこの幅であるなら、他の比較の精度もその幅を持つ。
「10/10 対 0/10」のような床と天井の比較は安全だが、中間の値の比較は信用できないことになる。

**設計。** 同一条件を3つの独立した run で n=5 ずつ回し、run 間分散そのものを測る。
条件を変えないので、出てくる差はすべて分散。

**規模。** 15セル / 30ターン。約 $4。

**判定。** run 間で 0/10〜4/10 の幅が再現するなら、**中間値での条件比較は今後やらない**方針にする。

### B-2. 人格残存度の段5／段4 の定義

**現状。** 「地図を渡してから確認する」形が段5か段4か未定義。
006 では一致 20/20 だったが、003 の再採点では 3/10 まで落ちた。**条件依存で不安定。**

**現時点で実害はない。** 結論はすべて「理解確認が先行」（二値）に依拠しており、
そちらは全 run で一致が高い。段5と段4はどちらも健全側なので区別が要らない。

**やるなら。** 段5を「地図も含めて、解説的な出力より前に確認がある」と定義し直し、
既存の判定済みデータを再採点して一致率を測る。新規セルは不要。

**規模。** 採点のみ。約 $2。

**判断。** 人格残存度を対外的な指標として使う予定がなければ、**やらなくてよい。**
二値の「理解確認が先行」を主指標として明記し、5段階は補助に降格するのが素直。

## 優先度C ── 当初計画の4要因

001 の前に立てた計画では、5要因を測る予定だった。コンテキストの1つは終わったので残り4つ。

**ただし前提が変わった。** 2経路が分かったいま、**直前のターンの種類と質問の広さを統制しないと、
どの要因もこの効果に汚染される。** 全条件で loader を `list_only`（保持側）に固定して回すこと。

| ID | 要因 | 水準 | 規模 |
|---|---|---|---|
| C-1 | **自己開示量** | 仮説あり＋エラー全文 / 仮説なし＋全文 / 仮説あり＋一部 / どちらも無し | 4 × n=5 = 20セル |
| C-2 | **言葉遣い** | 丁寧 / カジュアル / 命令形 / 圧（「もういいから答え教えて」） | 4 × n=5 = 20セル |
| C-3 | **レベル信号** | 初学者語彙 / 経験者語彙 | 2 × n=5 = 10セル |
| C-4 | **タスク粒度** | 粗 / 中 / 細 | 3 × n=5 = 15セル |

**C-1 を先に。** トラブルモードの5点セット収集に直結し、A-1 と同じ素材で回せる。
「仮説を聞いたか」は規定が明確で判定しやすい。

**C-2 の「圧」水準が特に価値がある。** プロンプトには
「粘られたときの対応」としてヒントを3段階で具体化する手順があるが、**これも未測定**。
「もういいから答えを教えて」と3回続けたときに完成コードを出すかどうかは、
運用上いちばん怖い失敗なので、単独で測る価値がある。

**C-4 は優先度が低い。** 粒度の効果は 002〜006 で実質的に測り終えている。

**規模合計。** 65セル / 130ターン。約 $16。

## 優先度D ── 多ターンでしか測れない規定

**現状。** 全実験が2ターンで、3ターン目以降の規定は一切測っていない。

| 未測定の規定 | 出典 |
|---|---|
| はしごを降りる／降りたら次は上げる | prompt.md L76-77 |
| **L4（選択）で答えられたら L3（予測）へ上げる** ★2026-09-08 追加 | L80 |
| 同じところで3往復したら前提の解説に切り替える | L294 |
| 返事が短くなったら段を下げる | L128 |
| セッションの終わり方（要約を求める、重くしない） | L298-305 |

**「1セッションで深く掘るのは2箇所まで」の行は消した。** 規定そのものを撤廃したため、測る対象がない。

**新しく入った「L4で答えられたら L3 へ上げる」は、多ターンでしか測れない。**
1ターン目では最初の問いしか出ないので、上げ下げは観測できない。D の設計にそのまま乗る。

**設計の難所。** 学習者の2・3ターン目を固定文にすると、メンターが何を聞いてきても
成立する内容中立な文が必要になる。たとえば
「うーん、たぶんデータを取ってくるやつだと思うんですけど、正直あんまり分かってないです」。

「3往復ルール」を測るには**わざと詰まり続ける台本**が要る。
3ターン連続で「分かりません」と返し、4ターン目で解説に切り替わるかを見る。

**規模。** 5ターン × 3条件 × n=5 = 15セル / 75ターン。約 $10。

**優先度。** A-1・A-2 の後。実学習者の観察（A-2）で多ターンの崩れ方が見えてから
設計したほうが、当てずっぽうな台本を書かずに済む。

## 測ることをやめた方がよいもの

- **コンテキスト量を独立変数として扱うこと。** 004 で否定された。
  Claude Code のバックグラウンド先読みにより、質問の粒度がコンテキスト量を決めてしまうため、
  そもそも独立に操作できない。**量は結果として記録するに留める**
- **`問い返し密度`。** 字数と交絡し、日本語の疑問形も取りこぼす。参考値以上には使わない
- **人格残存度の5段階を主指標にすること。** B-2 のとおり、二値のほうが安定している
