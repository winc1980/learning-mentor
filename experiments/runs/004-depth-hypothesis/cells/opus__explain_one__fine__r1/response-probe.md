## 結論から

`10` は **「ハッシュの計算を何回繰り返すか」を決めるつまみ**です。bcrypt では「コストファクター（cost factor）」と呼びます。

そして重要なのが、10 は回数そのものではなく **2の指数** だということ。

```
10 → 2^10 = 1024 回
11 → 2^11 = 2048 回
12 → 2^12 = 4096 回
```

つまり **1増えるごとに、計算時間が倍になります。**

## なぜ「何回も繰り返す」必要があるのか

ここが本題です。

まず前提として、ハッシュ化とは「元に戻せない形に変換すること」です。パスワードを平文のまま DB に保存すると、DB が漏れた瞬間に全員のパスワードが露出する。だから変換して保存し、ログイン時は「入力されたパスワードを同じ手順で変換して、保存済みの値と一致するか」で照合します。7行目と13行目がまさにその2つですね。

さて、普通のハッシュ関数（SHA-256 など）は **速いことが正義**です。ファイルの改ざんチェックなどで大量に計算するので。

ところが**パスワードに限っては、速さが弱点になります。**

攻撃者が DB を盗んだとしましょう。ハッシュ値は元に戻せませんが、攻撃者は別の手が使えます。「よく使われるパスワードを片っ端からハッシュ化して、盗んだ値と一致するか試す」——総当たりです。

このとき、1回のハッシュ計算が速ければ速いほど、攻撃者は単位時間あたりに多く試せます。GPU を使えば秒間数十億回という規模になります。

だから bcrypt は発想を逆にしました。**わざと遅くする。**

1024回も繰り返せば、1回の計算に数十〜100ミリ秒ほどかかります。正規のユーザーがログインするときは 0.1 秒待つだけなので誰も困りません。しかし総当たりする側は、試行回数がそのまま数千分の1に落ちます。

**この「正規利用者にはほぼ無害だが、攻撃者には致命的」という非対称性が、コストファクターの狙いです。**
