```
`app/lib/hash.ts` を読みました。この `10` は、**「計算をどれだけ重くするか」を指定する数字**です。

## まず、直感に反するところから

普通、処理は**速いほうが良い**ですよね。でもパスワードのハッシュ化だけは逆で、**遅いほうが良い**んです。

理由はこうです。攻撃者がDBを丸ごと盗んだとします。中に入っているのはハッシュ化されたパスワードだけ。攻撃者はここから元のパスワードを当てるために、「`password123` をハッシュ化してみる → 一致しない → `qwerty` を試す → …」と総当たりします。

このとき、1回のハッシュ化に **0.00001秒**しかかからなければ、攻撃者は1秒で10万個試せます。
1回に **0.1秒**かかれば、1秒で10個しか試せません。**1万倍の差**です。

つまり、ハッシュ化を意図的に遅くすることが、そのまま防御力になります。bcrypt はそのために作られたアルゴリズムで、`SALT_ROUNDS` はその**遅さのつまみ**です。

## 10 という数字そのもの

これは「10回」ではありません。**2の10乗 = 1024回**、内部の重い処理を繰り返します。

指数なので、つまみを1つ回すと**時間が2倍**になります。

| 値 | 内部の繰り返し | 時間 |
|---|---|---|
| 10 | 1,024回 | 基準（だいたい 50〜100ms） |
| 11 | 2,048回 | 2倍 |
| 12 | 4,096回 | 4倍 |

ちなみに `SALT_ROUNDS`（bcrypt の用語では cost factor / work factor）という名前は少し紛らわしくて、「ソルトを何回振るか」ではありません。**コストの指数**です。

## 「なぜ？」が3つあります

### なぜ JWT と Cookieセッション の2重なのか

Cookieセッション自体、`secrets: [SESSION_SECRET]` で署名されているので、**中身の改ざんはそれだけで防げています**。なのに中身をさらにJWTにしている。

考えられる理由：
- **有効期限を JWT 側で持てる**（`expiration = "30d"`）
- **Cookie の外でも使える形**になる（Authorizationヘッダなど、将来API化するとき）
- 責務の分離（「運ぶ手段」と「身分証明」を別にする）

一方で「このアプリの用途では冗長」という見方も成り立ちます。**設計判断として一択ではない**ところなので、そう読んでおいてください。

### なぜ JWT を検証した後に、わざわざDBを引くのか

JWT に `id: 3` と書いてあって署名も正しいなら、それを信じればDBアクセスを1回減らせます。それでも `getById()` しています。

**JWTは発行した瞬間の情報で固まっているから**です。30日有効ということは、退会したユーザーの紙が最大30日間有効なままになる。名前を変えても古い名前のまま。だからDBに毎回聞き直している。代償は**全リクエストでDBアクセス1回**です。これは典型的なトレードオフです。

### `redirectAfterAuth` は何のためにあるのか

`session.flash("redirectAfterAuth", request.url)` — **flash** は「次の1回読んだら消える」タイプの保存です。

未ログインで `/app/live/3/timetable` を開くと、その URL を控えてからログイン画面へ飛ばす。ログイン成功時に `login.tsx` の125行目が読み出して、そこへ戻す。**トップに戻されずに元のページへ戻れる**のはこの仕組みです。

### メンターの応答

```
`app/lib/hash.ts` を読みました。先に結論から言うと、**この `10` は「計算をどれくらい重くするか」を決める数字**です。回数そのものではなく、**指数**です。

## 何の数字か

bcrypt は内部で鍵を作り直す処理を繰り返します。その繰り返し回数が `2^10 = 1024` 回になる、という指定です。この値は**コストファクター**と呼ばれます。

指数なので、**1増えると処理時間が2倍**になります。

| 値 | 繰り返し回数 | ざっくりの時間感 |
|---|---|---|
| 10 | 1,024 | 数十ミリ秒 |
| 11 | 2,048 | その2倍 |
| 15 | 32,768 | 10 の32倍 |

## なぜ「わざと重く」するのか（ここが本題）

普通、ハッシュ関数は**速いほど良い**とされます。ファイルの改ざん検出などでは速さが価値です。

でもパスワードの保存では、**その速さがそのまま攻撃者の武器になります。**

データベースが漏洩したとして、攻撃者の手元にあるのはハッシュ値だけです。元のパスワードは分かりません。そこで攻撃者は「よくあるパスワードを片っ端からハッシュ化して、一致するものを探す」という総当たりをします。

このとき、1回のハッシュ化が0.001ミリ秒なら、1秒間に何億通りも試せてしまう。1回に50ミリ秒かかるなら、同じ1秒で20通りしか試せない。**攻撃コストが数百万倍になります。**

一方、正規のログインでハッシュ化されるのは1回だけなので、50ミリ秒は誰も気にしません。**攻撃者だけに重くのしかかる**という非対称性を作るのが目的です。だから bcrypt には、SHA-256 のような普通のハッシュ関数にはない「重さを選べるツマミ」が付いています。

10 は bcrypt のライブラリで広く使われる既定値で、「安全性としては十分で、ログインの応答も体感で遅くならない」あたりの妥当な線として置かれています。

## なぜ変数名が「SALT_ROUNDS」なのか

**ソルト**というのは、ハッシュ化するときに混ぜるランダムな文字列のことです。これがあると、同じパスワードを使っている2人でも保存されるハッシュ値が違うものになり、「あらかじめ計算しておいたハッシュ一覧表」を使う攻撃が効かなくなります。

bcrypt では、このソルトを生成する処理とコストファクターの指定が同じ API にまとまっているため、慣習的に `SALT_ROUNDS` という名前が使われます。ただし実際に指定しているのは**ソルトの個数ではなく、コストの指数**です。名前が少し実態とずれている、という点は知っておくといいところです。

## 流れ①：ログインするとき（`login.tsx` の `action`）

上から順に、こう進みます。

```
メールでユーザーを探す
  → 見つからなければエラーを返して終わり
パスワードを照合する（bcrypt）
  → 合わなければエラーを返して終わり
signToken(user.id) で JWT を作る
  → session に "sessionToken" として入れる
Set-Cookie を付けてリダイレクト
```

ポイントは **JWTの中身が `{ id: 数値 }` だけ**だということです（`jwt.ts` の `JWTSessionPayloadSchema`）。名前もメールも入っていません。ユーザーIDだけ。

## 流れ②：ログイン後にページを開くとき（`user.ts`）

`middlewares/user.ts` は、上から下へ**関門が4つ**並んでいます。

```
1. Cookieに sessionToken があるか？        なければ → /auth/login
2. verifyToken で検証できるか？            ダメなら → /auth/login
3. payload.id でDBからユーザーを引けたか？  失敗なら → /auth/login
4. そのユーザーは実在したか（null でない）？ null なら → /auth/login
   ↓ 全部通過
   context.set(userContext, user)
```

だからあのファイルは `redirect("/auth/login")` が4回も出てきて長く見えるわけです。**4つの別々の失敗理由に、別々のメッセージを出しているだけ**で、構造は単純です。

そして最後の行、`context.set(userContext, user)` が肝です。ここでコンテキストに詰めておくと、この下のページは `context.get(userContext)` するだけでログイン中のユーザーを取れます。**各ページが認証チェックを書かなくていい**のは、これが理由です。

`app/routes.ts` で `app-middleware.tsx` が `/app` 配下の全部を囲っているので、**`/app` 以下は全ページが自動的にこの4関門を通ります。**

## ここが一番の「なぜ」── Cookie と JWT、なぜ両方あるのか

たぶんここが一番わかりにくいところだと思うので、先に言っておきます。

この2つは**競合する選択肢ではなく、担当が違います。**

- **JWT** = 通行証そのもの。「このIDのユーザーです」と書いてあり、**署名**が付いているので改ざんすると検出できる
- **Cookieセッション** = その通行証を**入れる封筒**。ブラウザに預けて、毎リクエスト自動で送り返させる仕組み

`sessions.ts` の cookie 設定を見ると、封筒側の守りが3つ付いています。

| 設定 | 何を防ぐか |
|---|---|
| `httpOnly: true` | JavaScriptからCookieを読めなくする |
| `sameSite: "lax"` | 他サイトからのリクエストに勝手に付いていくのを防ぐ |
| `secure: true` | HTTPS以外では送らない |

さらに `secrets: [SESSION_SECRET]` で**封筒自体にも署名**が付きます。なので、このアプリには**署名が二重にかかっています**（Cookie側の `SESSION_SECRET`、JWT側の `JWT_SECRET`）。`.env.example` に鍵が2つあるのはこのためです。
