## 結論から

この `10` は**「何回ハッシュ計算を繰り返すか」を決める数字**です。ただし「10回」ではありません。**2の10乗 = 1024回**です。

`SALT_ROUNDS` という変数名は、正直ちょっと誤解を招きます。bcrypt の世界ではこの数字を **cost factor（コスト係数）** と呼びます。ソルト（後述）の回数ではなく、計算の重さを決める指数です。

- `10` → 2¹⁰ = 1024回
- `11` → 2¹¹ = 2048回（10のちょうど2倍の時間）
- `12` → 4096回（4倍）

**1増えるたびに処理時間が2倍**になる、というのが一番大事な性質です。

## なぜわざわざ何度も繰り返すのか

ここが本題です。

普通のプログラムでは「速いほど良い」ですよね。でもパスワードのハッシュ化だけは逆で、**遅いほど良い**んです。

理由は、攻撃者の立場で考えると見えてきます。DBが漏洩して、ハッシュ化されたパスワードの一覧が盗まれたとします。攻撃者は元のパスワードを知りたい。でもハッシュは元に戻せないので、攻撃者がやるのは**総当たり**です。

> 「password」をハッシュ化してみる → 一致しない
> 「123456」をハッシュ化してみる → 一致しない
> 「qwerty」をハッシュ化してみる → 一致した！

つまり攻撃の速度は、**1回のハッシュ計算にかかる時間**で決まります。

ここで数字を入れてみます。仮に cost factor 10 で1回あたり 0.1秒 かかるとすると：

- **正規のユーザー**：ログイン時に0.1秒待つだけ。気にならない
- **攻撃者**：1秒に10個しか試せない。1億通り試すのに約115日

もしこれが普通の高速なハッシュ（SHA-256 など）だと、1回あたりマイクロ秒以下。GPUを使えば**1秒間に数十億回**試せてしまいます。1億通りなら一瞬で終わる。

**正規ユーザーが払うコストはごくわずかなのに、攻撃者のコストは何億倍にも膨らむ** ——この非対称性を意図的に作り出すための数字が、この `10` です。

## なぜ「10」なのか、大きくすればいいのでは

大きくすれば安全になりますが、その分**自分のサーバーも遅くなります**。ログインのたびに毎回その計算をするので、`16` などにするとログインに数秒かかり、同時アクセスが増えるとサーバーが詰まります。

つまりこの数字は「安全性 ⇄ レスポンス速度」のつまみです。慣習的には**1回あたり 100〜250ms 程度に収まる値**を選び、ハードウェアが速くなるにつれて年々上げていく、という運用をします。`10` は多くのライブラリのデフォルト付近で、無難な選択です。
