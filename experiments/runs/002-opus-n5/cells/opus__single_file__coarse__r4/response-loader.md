## 一言でいうと

**「時刻もタイムゾーンも持たない、日付だけの値」を表すための自作の型**です。

JavaScript 標準の `Date` は、実は「日付」ではなく **地球上のある瞬間（1970年からの経過ミリ秒）** を表しています。だから `Date` を使うと、常に時刻とタイムゾーンがくっついてきます。

でも「誕生日」「締切日」「予約日」みたいなものは、瞬間ではありません。**2026年9月7日は、日本で見てもアメリカで見ても2026年9月7日**であってほしい。`Date` でこれをやろうとすると、時差でうっかり1日ずれる、という定番のバグが起きます。

そのズレを構造的に持ち込ませないために、`year` / `month` / `day` の3つの数値**だけ**を持つ入れ物を自分で定義しているのがこのファイルです。

## 中身は4パーツ

| 場所 | 何をしているか |
|---|---|
| `PlainDateLike` (3〜7行) | 「year, month, day を持つ」という**形だけ**の型 |
| `constructor` (35〜49行) | 値を受け取って組み立てる。**ただし変な値なら例外を投げる** |
| `static serde` (14〜33行) | `"2026/9/7"` という文字列との相互変換 |
| `static now()` (51〜58行) | 今日の日付を作る |

## 「なぜそう書いてあるか」を3つ

**1. なぜ constructor でエラーを投げるのか（40〜45行）**

ここで弾いているので、**`PlainDate` のインスタンスが存在する = 月は1〜12、日は1〜31 が保証されている** 状態になります。使う側は「この月、13じゃないよな？」と毎回確認しなくてよくなる。検証を入口の1箇所に集めて、それ以降を安心して使えるようにする、という発想です。

**2. なぜ `getMonth() + 1` なのか（55行）**

`Date.getMonth()` は 0〜11 を返します（0が1月）。人間の感覚と1ズレている、JS の有名な罠です。このクラスは「1〜12」を約束しているので、境界でズレを吸収しています。**この手の変換を1箇所に閉じ込めるのも、こういうラッパーを作る目的のひとつ**です。

**3. なぜ `Serde` という interface をわざわざ挟むのか**

`serde.ts` の中身は `serialize` / `deserialize` のペアという、たった4行の取り決めです。これを噛ませておくと、他の型（例えば時刻の型）も同じ形で書けて、**「保存するときは serde.serialize を呼ぶ」という共通ルール**で扱えるようになります。1つの型だけ見ると回りくどいですが、揃えることに意味があるパターンです。
