## これは何のアプリか

`README.md` を見ると、これは **学習用の「軽音サークル ライブタイムテーブル」アプリ** です。普通のプロダクトリポジトリではなく、**ワークショップの教材**として作られています。

- 意図的に壊れている／未実装の箇所がある
- `issues/` に7つの課題（EASY〜EXTREME）が用意されている
- README に「生成AIにコードを書かせない」と明記されている

なので、このセッションが完成コードを出さないのは、教材の方針とも一致しています。

## ディレクトリの地図

```
├── app/              ← アプリ本体。ほぼここ
├── drizzle/          ← DBマイグレーションの履歴（自動生成。手で触らない）
├── scripts/setup/    ← 環境構築の自動化。GitHubのIssue作成やラベル設定など
```

`drizzle/` `scripts/` `issues/` は**課題を解くうえで直接いじる場所ではない**ので、当面は忘れて大丈夫です。

## app/ の中身 — ここが本体

大きく「**画面**」「**リクエスト処理の土台**」「**データ**」の3層に分かれています。

**画面まわり**
- `routes.ts` — URL とファイルの対応表。**ここが全体の目次**です
- `routes/` — 各ページ。1ファイルが1画面（＋そのサーバー処理）
- `components/ui/` — shadcn が生成したボタン・カード等の汎用部品（基本いじらない）
- `components/common/` — このアプリ独自の部品（`PasswordInput`、`DateInput` など）
- `hooks/` — 画面用のカスタムフック

**リクエスト処理の土台**
- `middlewares/` — 各ページの処理より**先に**走る共通処理。ログイン確認や、後述のリポジトリの受け渡しをしている
- `sessions/` — JWT とクッキーの扱い

**データまわり**
- `db/schema.ts` — テーブル定義。`live` `live_day` `user` `band` `band_participation` `band_availability` `live_application` の7つ
- `repositories/` — DB への読み書きを関数にまとめた層。SQL 相当はここに閉じる
- `domain/entities/` — アプリ内で扱うデータの型（`Band` は `{id, name, leaderId}` だけの素朴な型）
- `lib/` — 汎用ユーティリティ（日付・時刻、`result.ts` によるエラー表現など）

## routes/ の構造が一番の特徴

`routes.ts` を読むと、URL がそのまま入れ子になっています。

```
/                       → 公開トップ
/auth/login,logout,register
/app/...                → ログイン必須エリア
    /app/live/:liveId/...        → 特定のライブ
        /band/:bandId/...        → そのライブの特定バンド
```

そして各階層に `〜-middleware.tsx` と `〜-layout.tsx` がペアで置かれています。ざっくり **middleware = 通す/弾く・データを用意する係**、**layout = 見た目の枠**、という役割分担です。この2つの違いは、あとで詳しく扱う価値があります。
