## 登場人物は4つ

| # | 何 | どこ |
|---|---|---|
| 1 | **パスワードのハッシュ** | `app/lib/hash.ts`（bcrypt） |
| 2 | **JWT** | `app/sessions/jwt.ts`（jose） |
| 3 | **Cookieセッション** | `app/sessions/sessions.ts` |
| 4 | **門番（middleware）** | `app/middlewares/user.ts` |

比喩で言うと：

- **1** は「合言葉の照合」
- **2** は「あなたはユーザーID 3 番です、と書かれた**偽造できない紙**」
- **3** は「その紙を入れて持ち歩く、**鍵付きの封筒**」
- **4** は「ページに入る前に毎回封筒を開けて確認する**受付**」

**ここで一番の混乱ポイント**を先に言っておくと、**「紙（JWT）」と「封筒（Cookieセッション）」の2重構造になっている**ことです。どちらも "token" と呼ばれるので読んでいて混ざります。区別して読めるかどうかが山場です。

## 流れ①：ログインするとき

`app/routes/auth/login.tsx` の **`action`**（83行目以降）がサーバー側で走ります。

```
フォーム送信（mail, password）
 → userRepository.getByMail(mail)         … そのメールのユーザーいる？
 → authenticateWithPassword(id, password) … bcryptで照合
 → signToken(user.id)                     … 紙を作る（JWT）
 → session.set("sessionToken", token)     … 封筒に入れる
 → redirect("/app", { "Set-Cookie": ... }) … 封筒を渡してリダイレクト
```

`Set-Cookie` を返して初めてブラウザに封筒が渡ります。**`session.set()` しただけでは何も起きません**（メモリ上で書き換えただけ）。`commitSession()` して `Set-Cookie` ヘッダに載せる、この2手が必要です。ここは初見で必ず引っかかるところです。

## 流れ②：ログインが必要なページを開くとき

`app/routes.ts` を見ると、`/app` 以下は全部 `app-middleware.tsx` の内側に入っています。そして `app-middleware.tsx` は5行だけで、実体は `userMiddleware` です。

`app/middlewares/user.ts` がやっていること：

```
Cookieから封筒を取り出す
 → sessionToken が無い          → ログイン画面へ追い返す
 → verifyToken(sessionToken)    → 偽造・期限切れ → 追い返す
 → payload.id で userRepository.getById()
 → DBにいない                   → 追い返す
 → context.set(userContext, user)  ← ここで初めて通す
```

**なぜこの位置に置くのか**：ルートごとに「ログインチェック」を書くと、**1箇所書き忘れた瞬間に穴が開きます**。ルーティングの階層構造そのものに縛り付けておけば、`/app` 配下に新しいページを足しても自動で保護される。これが middleware をここに置いている理由です。

## 「なぜ？」が3つあります

### なぜ JWT と Cookieセッション の2重なのか

Cookieセッション自体、`secrets: [SESSION_SECRET]` で署名されているので、**中身の改ざんはそれだけで防げています**。なのに中身をさらにJWTにしている。

考えられる理由：
- **有効期限を JWT 側で持てる**（`expiration = "30d"`）
- **Cookie の外でも使える形**になる（Authorizationヘッダなど、将来API化するとき）
- 責務の分離（「運ぶ手段」と「身分証明」を別にする）

一方で「このアプリの用途では冗長」という見方も成り立ちます。**設計判断として一択ではない**ところなので、そう読んでおいてください。

### なぜ JWT を検証した後に、わざわざDBを引くのか

JWT に `id: 3` と書いてあって署名も正しいなら、それを信じればDBアクセスを1回減らせます。それでも `getById()` しています。

**JWTは発行した瞬間の情報で固まっているから**です。30日有効ということは、退会したユーザーの紙が最大30日間有効なままになる。名前を変えても古い名前のまま。だからDBに毎回聞き直している。代償は**全リクエストでDBアクセス1回**です。これは典型的なトレードオフです。

### `redirectAfterAuth` は何のためにあるのか

`session.flash("redirectAfterAuth", request.url)` — **flash** は「次の1回読んだら消える」タイプの保存です。

未ログインで `/app/live/3/timetable` を開くと、その URL を控えてからログイン画面へ飛ばす。ログイン成功時に `login.tsx` の125行目が読み出して、そこへ戻す。**トップに戻されずに元のページへ戻れる**のはこの仕組みです。
