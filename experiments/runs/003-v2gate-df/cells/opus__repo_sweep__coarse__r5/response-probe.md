認証は、このリポジトリの中で**一番ファイルが散らばっている領域**です。分からなくて当然の作りになっています。

さっきと同じやり方でいきます。**まず登場人物と場所だけ挙げます。それぞれが何をどうやっているかの説明は、まだしません。**

## 認証の登場人物（6つ）

| 役割 | 場所 |
|---|---|
| Cookie の入れ物を作る・読み書きする | `app/sessions/sessions.ts` |
| トークンの発行と検証 | `app/sessions/jwt.ts` |
| ログイン済みかを判定して、ダメなら弾く | `app/middlewares/user.ts` |
| 上の判定を「どのURLに適用するか」の指定 | `app/routes/app/app-middleware.tsx` と `app/routes.ts` |
| ログイン画面と、送信されたときの処理 | `app/routes/auth/login.tsx` |
| 登録画面 / ログアウト | `app/routes/auth/register.tsx` / `logout.tsx` |

周辺に2つ。パスワードのハッシュ化が `app/lib/hash.ts`、DB からユーザーを引くのが `app/repositories/user.ts` です。

地図として1つだけ補足すると、**Cookie（`sessions.ts`）と JWT（`jwt.ts`）が別ファイルに分かれていて、この2つは役割が違います。** ここが認証まわりで一番混乱しやすい分岐点なので、頭の隅に置いておいてください。

あと事実として、`logout.tsx` は**画面だけあって処理が入っていません**（7行のファイルです）。壊れている箇所の一つかもしれません。

## どこから見ますか

よくある入り口を挙げます。1つ選んでください。「全部ぼんやり」でも大丈夫です。

- **①** ログインボタンを押してから `/app` に着くまでに何が起きるか（`login.tsx`）
- **②** ログイン済みかどうかを、次のリクエストでどうやって思い出しているのか（`user.ts`）
- **③** なぜ Cookie と JWT の**両方**が要るのか（設計の理由の話）
- **④** パスワードはどう保存されているのか
- **⑤** 未ログインで弾かれた後、ログインしたら元のページに戻る仕組み

個人的には **③ → ② → ①** の順が一番ほどけやすいと思っていますが、決めるのはあなたです。
