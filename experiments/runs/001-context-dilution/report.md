> 正しい結論は「**粗い質問と埋まったコンテキストが揃ったときにだけ崩れる**」という交互作用。
>
> また本文の人格残存度は**旧ルーブリック**による採点で、現象と逆に動いていた

> `judgments.jsonl` は新ルーブリックで採点し直したもの。
>
> **記録として残すが、結論として引用しないこと。**

fixture `913c103e` は全セル実行前後で無改変。claude 2.1.263。

**結論（暫定）：希釈は起きる。ただし opus のみで、コンテキスト量に依存し、粒度には依存しない。**

## 1. 実験設計に関わる発見：バックグラウンド先読みがある

**全セルで `iterations=1`、モデルのツール往復はゼロ。** それでもコンテキストは
10,061 → 31,715 tok まで変動した。`repo_sweep` の loader 応答は「リポジトリの中身を
一通り見てきました」と述べ、`package.json` と README を正確に引用している。
**モデルは Read を一度も呼んでいない。** Claude Code のバックグラウンド先読みが、
ツール呼び出しを経ずにファイルをコンテキストへ入れている。

**これが意味すること：粗い質問を投げること自体がコンテキストを膨らませる。**
loader が同一文（`none`）でも、probe の粒度だけで開始コンテキストが変わる。

| | fine | coarse | 差 |
|---|---|---|---|
| sonnet / none | 11,258 | 20,473 | **+9,215** |
| opus / none | 10,061 | 18,943 | **+8,882** |

probe 文の長さの差は約20字。この9k tok は先読みによるもの。
粒度と量は独立変数ではない。分離するには、**量が近く粒度が違うセルの対**を見るしかない（下記3）。

## 2. 使える指標と、使えなかった指標

採点者2名の一致：

| 項目 | 一致 |
|---|---|
| モード / 最初の問い / **理解確認が先行** / 完成コード相当 | **12/12** |
| 人格残存度 | 9/12 |

### 使えなかった指標① 人格残存度（rubric.md の1〜5）

**現象と逆に動いた。** 最悪の応答である F（opus / repo_sweep / coarse、4,163字の一方的解説）に
**両採点者が満点の5** を付けている。一方で採点者自身の根拠欄はこう書いている。

> 「ね口調と定型文あり。**ただし確認なしで全部説明**」
> 「設計理由の説明は厚いが、**確認は解説の後に置かれている**」

原因はスケールの構造にある。段5・4 は口調と定型文（「ね」／「正確じゃなくて大丈夫です」）で
定義され、段3〜1 は問いかけの有無で定義されている。**軸が2本混ざっている。**
温かい口調で長々と一方的に解説する応答は、上の軸では満点、下の軸では最低点になり、
採点者は上を取った。

→ **段5・4を口調ではなく「理解確認が解説より前にあるか」で定義し直す必要がある。**
なお段5の例文は GitHub MCP と issue #16 に言及しているが、本実験は MCP を全停止しているため
本来この段は到達不可能だった。採点者は口調部分だけを見て5を付けている。

### 使えなかった指標② 問い返し密度（私の実装ミス）

`？` の個数で数えていたが、日本語の質問は「〜ですか**。**」と句点で終わることが多い。
opus / none / coarse は `？` が0件だが、実際には選択肢つきの確認質問を2つ含む。
**この指標に基づく「問いが1つも無い」という判断は誤り。**
run.py を修正済み（`質問文数` に「〜か。」を加算）。ただし完全ではない。

### 使えた指標 理解確認が先行

**解説を始める前に**相手の理解を確かめる問いがあるか。採点者2名が12/12で一致した。
これが本体プロンプト [:152-162](../../../learning-mentor-prompt.md#L152-L162) の中核であり、
実質的にこの実験の主要指標になった。

## 3. 結果

コンテキスト量の昇順に並べる。

### opus

| ctx | lbl | load | grain | 理解確認が先行 |
|---|---|---|---|---|
| 10,061 | A | none | fine | **T** |
| 12,541 | C | single_file | fine | **T** |
| 18,943 | B | none | **coarse** | **T** |
| 20,390 | D | single_file | **coarse** | **F** |
| 20,803 | E | repo_sweep | fine | **F** |
| 26,842 | F | repo_sweep | **coarse** | **F** |

**約20,000トークンを境に、例外なく反転している。**

そして粒度は効いていない。

- **B は coarse なのに保たれている**（18,943）
- **E は fine なのに崩れている**（20,803）

この2セルはコンテキスト量の差が2%未満で、粒度が逆。**粒度で決まるなら B が崩れ E が保たれるはずで、
結果は逆になっている。**

### sonnet

| ctx | lbl | 理解確認が先行 |
|---|---|---|
| 11,258 | A | T |
| 13,145 | C | T |
| 20,473 | B | T |
| 21,090 | D | **F** |
| 25,407 | E | T |
| 31,715 | F | T |

単調でない。D だけが F で、それより上の E・F は T に戻っている。
D の根拠欄は「動機確認で理解度確認ではない」— 希釈ではなく別の振る舞い。
**sonnet には希釈のパターンが見えない。**

### 統計的な重み

opus の6点が量の順に完全に3つずつ分かれる確率は、偶然なら 1/C(6,3) = **1/20（5%）**。
n=1 での 6点として、これは示唆としては強いが確定ではない。

## 4. 何が起きているか（実例）

**opus / A（ctx 10,061）— 保たれている。L3 の選択肢で前提を確認し、解説を保留している：**

> `bcrypt.hash(password, SALT_ROUNDS)` の第2引数に渡っている数字ですね。
> 先に一つだけ確認させてください。**「ハッシュ化」** と **「ソルト」** …どのあたりまで馴染みがありますか？
> - **A:** どっちも初めて聞く／**B:** ハッシュ化はなんとなく分かる／ソルトは知らない

**opus / F（ctx 26,842）— ご報告の現象そのもの。先に4,163字を全部書き切っている：**

> 読み終わりました。順番に説明します。まず**全体の骨格**から、そのあと具体的な流れに降ります。
> ## まず骨格：認証は「2階建て」になっています

以降、17行のフロー図を含むブロック4つで `userRepository.getByMail()` `signToken(user.id)`
`InvalidPasswordError` などプロジェクト固有 API を並べた設計解説が続く。
理解確認は **4,163字すべてを説明し終えた最後** に置かれている。
[prompt.md:24](../../../learning-mentor-prompt.md#L24)（プロジェクトの識別子を使わない）と
[:167](../../../learning-mentor-prompt.md#L167)（1回に1つ）に抵触。

固有識別子の混入は D（3個）と F（6個）でのみ発生し、いずれも「理解確認が先行 = F」のセル。

## 5. 対処案

### モデルを上げても解決しない。むしろ逆

opus のほうが希釈が激しい。応答字数は 404 → 4,163 と10倍になる。
sonnet は全条件で114〜351字に収まり、コードブロックを一度も出さなかった。
**「大事な場面では上位モデルを使う」という運用指針は、この件に関しては誤り。**

### 効くとすればプロンプト側

現状のプロンプト [:156-157](../../../learning-mentor-prompt.md#L156-L157) は
「全体像を先に、詳細は後で」と書いている。これは**解説を始めてよいと決まった後**の順序の話だが、
コンテキストが埋まった状態では **[:152](../../../learning-mentor-prompt.md#L152)「何が分かっていないのかを特定する」を
飛ばして、いきなり全体像から書き始める**読み方に倒れている可能性がある。

検討すべき修正（n を増やして確認してから）：

1. **手順1を飛ばせない形にする。** 「材料が揃っているときほど、先に書き始めたくなる。
   材料の多さは、理解度を確認しない理由にならない」を明示する
2. **書き始める前の字数の歯止め。** [:167](../../../learning-mentor-prompt.md#L167)「1回に1つ」を、
   最初の応答の目安字数として具体化する
3. **粗い質問への分岐は優先度が低い。** 今回のデータでは粒度は効いていない

## 6. 次にやること

1. **rubric.md の人格残存度を定義し直す。** 口調ではなく「理解確認が解説より前か」を軸にする。
   いまのスケールのままでは希釈を検出できない（F に満点が付く）
2. **opus で n=3〜5 に増やす。** 20,000tok の境界が再現するかを見る。
   sonnet は効果が見えないので後回しでよい。opus 6セル × n=5 で約 $6
3. **境界を狙った水準の追加。** 現状 18,943 と 20,390 の間に何もない。
   loader を調整して 19k / 20k / 21k 付近を厚くすると、閾値の位置が絞れる
4. **002〜005 は 001 の後。** 希釈がコンテキスト量で決まるなら、他の要因を測るときも
   **開始コンテキスト量を揃える**必要がある。揃えずに測ると全部この効果に汚染される
