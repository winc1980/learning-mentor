`app/lib/hash.ts` を見ました。まず名前から入ると、ここは引っかかって当然の場所です。

## 先に結論

`SALT_ROUNDS` という名前ですが、**塩（salt）の量や長さのことではありません。** これは「ハッシュ計算を何回繰り返すか」を決める数字で、一般には **コストファクター（cost factor）** と呼ばれます。

しかも「10回」ではありません。**2の10乗 = 1024回** です。指数です。

つまり `11` にすると 2048回、`12` にすると 4096回。**1増やすと計算量が2倍になります。**

（前提の確認を1つだけ。「ハッシュ化＝元のパスワードに戻せない一方向の変換」というところは大丈夫ですか？ 怪しければそこから話します。）

## なぜ「わざと繰り返す」のか

ここが本題です。普通、計算は速いほうがいいですよね。でもパスワードのハッシュだけは逆で、**わざと遅くしたい。**

理由は、攻撃者の立場に立つと見えます。

DBが盗まれたとします。攻撃者の手元にあるのはハッシュ値だけで、元のパスワードは分かりません。そこで攻撃者は「`password123` を試しにハッシュ化してみる → 盗んだ値と一致するか比べる」を、ひたすら総当たりで繰り返します。

- ハッシュ計算が **1回0.000001秒** なら、1秒間に数百万個試せる
- ハッシュ計算が **1回0.1秒** なら、1秒間に10個しか試せない

攻撃者の総当たりの速度が、そのまま10万分の1になります。一方、正規のログインは1回だけなので、0.1秒待たされても人間には気になりません。**攻撃者にだけ重くのしかかるコスト**なんです。

だから bcrypt には「どれだけ遅くするか」のつまみが付いていて、それが `10` という数字です。

## じゃあ salt はどこに行ったのか

`bcrypt.hash(password, 10)` の第2引数は数値ですが、bcrypt は内部で **ランダムな salt を自動生成して勝手に混ぜてくれます。** だから自分で salt を作るコードがここには無い。名前が `SALT_ROUNDS` なのは、bcrypt の API の歴史的な事情で、実態とややズレた呼び方が定着したものです。

## ここで1つ、予想してみてください

正解を当てにいかなくて大丈夫です。「たぶん〜」で構いません。

`hashPassword` は `SALT_ROUNDS` を渡していますが、下の `compareHashedPassword`（13行目）は **`SALT_ROUNDS` を渡していません。** `password` と `passwordhash` の2つだけです。

照合するには「同じ条件でハッシュ化して比べる」必要があるはずなのに、コスト（1024回）も salt も渡していない。

**bcrypt.compare は、それをどこから知るんだと思いますか？**

- A: bcrypt がライブラリ内部にデフォルト値を持っている
- B: 保存されているハッシュ文字列そのものに書いてある
- C: 実は照合には salt もコストも要らない
- D: 分からない

D でも全く問題ありません。ここが分かると、DBの `passwordHash` カラム（`app/db/schema.ts` の `userTable`）に何が入っているのかが一気に腑に落ちます。
