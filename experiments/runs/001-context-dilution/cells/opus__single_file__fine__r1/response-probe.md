## 一言で言うと

`10` は **「ハッシュ計算を何回繰り返すか」を決める数字**です。ポイントは2つあります。

1. **10回ではありません。** 2の10乗 = **1024回**繰り返す、という意味です（指数で指定します）
2. この数字を大きくすると、**わざと計算が遅くなります**

## なぜ、わざと遅くするのか

ここが一番の「なぜ」です。

普通のプログラムでは速いほうが良いのに、パスワードのハッシュだけは逆です。理由は、**攻撃者の総当たりも同じだけ遅くなるから**。

仮にDBが漏れたとして、攻撃者は「よくあるパスワード」を片っ端からハッシュ化して、漏れたハッシュと突き合わせます。このとき、

- 1回のハッシュ計算が **0.001秒** なら、1秒で1000個試せる
- 1回が **0.1秒** なら、1秒で10個しか試せない

正規のユーザーは、ログイン時に1回だけ0.1秒待つだけ。ほぼ気になりません。でも攻撃者にとっては、試行回数が1万倍のコストになります。**守る側の負担はほぼゼロで、攻める側だけが重くなる**——この非対称性を作るための数字です。

だから「速いハッシュ」は、パスワード保存には向きません（SHA-256をそのまま使ってはいけない、と言われるのはこの理由です）。

## なぜ固定値ではなく、設定可能なのか

ハードウェアは年々速くなるからです。10年前に十分だった回数は、今のGPUでは一瞬で終わります。だから bcrypt は**後から上げられる**設計になっていて、`10` はいわば「今の時代の妥当ライン」です。

適切な値は「自分のサーバーで実測して、1回あたり数百ミリ秒程度に収まる最大値」という決め方をします。10 は一般的な既定値で、12あたりを推奨する意見もあります。**このプロジェクトにとって適切かどうかは、実測しないと分かりません。**

## ついでに：名前の `SALT_ROUNDS` について

変数名に `SALT` とありますが、**この数字自体はソルトではありません。** ソルト（各パスワードごとに付ける乱数）は bcrypt が**自動で生成して、結果のハッシュ文字列の中に埋め込んで**くれます。

これが分かると、13行目の `bcrypt.compare(password, passwordhash)` に**ソルトを渡していない**理由が説明できます。第2引数のハッシュ文字列を見れば、そこからソルトを取り出せるからです。
