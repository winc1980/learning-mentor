## まず骨格：認証は「2階建て」になっています

ここが一番の勘所です。このアプリのログイン状態は、**入れ物**と**中身**の2層でできています。

```
┌─ 1階：Cookieセッション ─────────────────┐
│  ブラウザのCookie「__session」          │
│  React Router が署名して改ざんを防ぐ     │
│                                          │
│   中に入っているもの:                    │
│   ┌─ 2階：JWT ────────────────────┐    │
│   │  sessionToken = "eyJhb..."     │    │
│   │  中身は { id: 3 } だけ          │    │
│   │  有効期限30日、HS256で署名      │    │
│   └────────────────────────────────┘    │
│   toastPayload（1回で消える通知）        │
│   redirectAfterAuth（1回で消える）       │
└──────────────────────────────────────────┘
```

**「Cookieの中にJWTが入っている」** という入れ子構造です。ここを掴むと、あとのファイルが全部つながります。

## 流れ① ログインするとき

`login.tsx` の下半分、`action` 関数がやっていることです。

```
フォーム送信 (POST /auth/login)
        │
        ▼
① メールアドレスでユーザーをDBから探す        userRepository.getByMail()
        │  見つからなければ UserNotFoundError
        ▼
② パスワードを照合                     authenticateWithPassword()
        │  中で bcrypt.compare を呼んでいる
        │  違えば InvalidPasswordError
        ▼
③ JWTを発行                            signToken(user.id)
        │  → { id: 3 } を秘密鍵で署名した文字列
        ▼
④ それをCookieセッションに詰める          session.set("sessionToken", token)
        │
        ▼
⑤ Set-Cookie ヘッダを付けてリダイレクト
```

ここでパスワードについて一点。DBに保存されているのは**パスワードそのものではなくbcryptのハッシュ**です。`hash.ts` に `compareHashedPassword` はあっても「復号する関数」が無いのはそのためで、**元に戻せないのが正しい**んです。照合は「入力をもう一度ハッシュ化して、保存済みハッシュと突き合わせる」という形でやっています。

ここまでで一区切りです。大丈夫そうですか？

## 流れ② ログインが必要なページを開くとき

`/app/` 以下すべてがこの門番を通ります。取り付けているのは `app-middleware.tsx` のこの1行だけです。

```tsx
export const middleware: Route.MiddlewareFunction[] = [userMiddleware]
```

そして `middlewares/user.ts` が実際の門番です。**上から順に「ダメな条件」を潰していく構造**になっています。

```
リクエスト到着
    │
    ├─ Cookieに sessionToken が無い？ ──────→ /auth/login へ
    ├─ JWTの署名が不正 / 期限切れ？ ────────→ /auth/login へ
    ├─ JWTの中の id でDBを引けなかった？ ───→ /auth/login へ
    ├─ そのユーザーがもう存在しない？ ───────→ /auth/login へ
    │
    ▼ 全部くぐり抜けた
context.set(userContext, user)    ← ここで初めて「ログイン中のユーザー」が確定
```

最後の1行が肝です。**この先のページは `context.get(userContext)` を書くだけでユーザーを取れて、しかも `null` チェックが要りません。** 門番が通した時点で存在が保証されているからです。

前回説明した `live-middleware` / `band-middleware` も、これと同じ形をしています。「入る前に検証して、context に確定した値を置く」というパターンの繰り返しです。

## なぜこの設計なのか（ここが本題かもしれません）

**なぜ JWT に `id` しか入れないのか。名前もメールも入れれば、DBを引かなくて済むのに。**

`jwt.ts` を見ると、ペイロードは本当に `{ id: number }` だけです。そして `user.ts` の門番は、**毎リクエストDBを引き直しています**。一見むだですが、理由があります。

- JWTは発行した瞬間の情報を30日間持ち歩きます。**名前を入れたら、改名しても30日間古い名前のまま**です
- 退会したユーザーのJWTも、期限内なら署名検証は通ってしまいます。DBを引くから「存在しないユーザー」を弾ける
- つまり **JWTは「本人であること」の証明だけに使い、「今どういうユーザーか」は毎回DBに聞く** という役割分担です

**なぜ Cookie の中にわざわざ JWT を入れるのか（二重に見える）。**

これは正直、**設計上の議論の余地がある部分**です。Cookieセッション自体すでに署名されているので、`{ userId: 3 }` を直接入れても動きます。実際にそうしているアプリも多いです。このリポジトリが2階建てにしているのは、有効期限をJWT側で管理できる・将来トークンを別経路（APIなど）で使い回せる、といった利点を取ったものと読めます。**「必ずこうすべき」ではありません。**

## おまけ：flash という仕掛け

`session.flash(...)` が何度か出てきます。`set` との違いは、**一度読み出したら自動で消える**ことです。使われ方は2つ。

- `toastPayload` … 「ログインしました」の通知。リダイレクト先で1回表示したら消える
- `redirectAfterAuth` … **元々開こうとしていたURL**。門番が保存しておいて、ログイン成功後にそこへ戻す（`login.tsx` の最後、`redirect(redirectUrl ?? "/app")`）
